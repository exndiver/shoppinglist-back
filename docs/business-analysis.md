# Бизнес-аналитика и ТЗ домена / API

Документ фиксирует суть backend’а для продукта **shopping + цены + синхронизация** (shared — отдельная будущая фича). Без привязки к финальной реализации эндпоинтов на уровне кода — это **домен, инварианты и поведение**, на основе которых строится API и схема БД.

---

## 0. Цель системы

Хранить и синхронизировать реальные объекты покупок (**товары, магазины, цены, списки**) так, чтобы:

- данные были **консистентны**;
- **не дублировались** без явной доменной операции merge;
- цены корректно **агрегировались во времени** (история, не «прыгающее» состояние в списке).

---

## 1. Базовый принцип владения (owner-scoped)

**Все сущности принадлежат пользователю (owner).** Шаринг списков — отдельная фича (пока не реализуется), но модель к ней должна быть совместима.

Каждая сущность в общем случае имеет:

- `owner_id`
- `created_by` (например `device_id`)
- `updated_at`

### Следствия

- Любой запрос работает **только в рамках `owner_id`** из контекста аутентификации.
- **Дубликаты и merge** существуют **внутри одного пользователя**. Merge **между разными owners запрещён**.
- **Нет глобальной базы товаров** для всех пользователей: один и тот же реальный товар у двух пользователей — **две независимые записи** с разными ценами — это норма.

### Подготовка к шарингу

В будущем шарится **список**, а не «все данные пользователя». Товары остаются у владельца; список — shared-контекст (появятся cross-owner ссылки). Поэтому **уже сейчас у всех сущностей есть `owner_id`**.

---

## 2. Доменная модель

### 2.1 User (owner)

Логический владелец данных. На старте может совпадать с идентификатором устройства; позже — полноценный аккаунт.

### 2.2 Good / товар

Реальный объект покупки (молоко, хлеб и т.д.) **в разрезе одного owner**.

- Единая **каноническая** точка для данных о товаре у этого пользователя.
- Допускаются **алиасы / merge**, но все должны указывать на **canonical** (`merged_into` или аналог).

**Инварианты**

- Один реальный товар у пользователя → один **canonical** товар (запись `goods`) после устранения дубликатов.
- Идентификатор immutable; «удаление» — через soft-delete или merge, не физический delete в доменной модели.

### 2.3 Store (магазин)

Место покупки **пользователя**.

**Инварианты**

- Уникальность по смыслу через нормализацию имени; возможны несколько записей → **merge** внутри owner.

### 2.4 Offer (наличие товара в магазине)

Связка **товар + магазин** в рамках **одного owner**.

**Инвариант**

- Уникальность: **`(owner_id, good_id, store_id)`** (или эквивалент с каноническими id после resolve).

Цену Offer **не хранит** — только факт связи «этот товар продаётся в этом магазине».

### 2.5 PriceRecord (цена во времени)

Событие: «цена товара X в магазине Y в момент T» для данного owner.

**Инварианты**

- **Append-only**: записи не обновляются, только добавляются.
- Актуальная цена = **последняя по времени** (`recorded_at`) для данного offer.

### 2.6 Shopping List

Контекст покупки (поход в магазин), принадлежит owner.

### 2.7 ListItem

Конкретное намерение купить.

**Инварианты**

- В списке используется **snapshot цены** на момент добавления — цена в пункте списка не должна «прыгать» при изменении рыночной цены.

### 2.8 Identity (external linkage)

Связь с внешними источниками / другими представлениями для **дедупликации и синка**.

**Инвариант (scoped)**

- Уникальность: **`(owner_id, external_id, source)`**.

---

## 3. Ключевые бизнес-проблемы

| Проблема | Суть |
|----------|------|
| Дубликаты | Несколько записей → один реальный объект → без merge ломаются цены и UX |
| Время | Цена — поток событий, не просто поле «текущая цена» |
| Синхронизация | Данные создаются на разных устройствах |
| Shared | Несколько пользователей на один список — позже, модель не должна ломаться |

---

## 4. Бизнес-решения (ядро)

1. **Canonicalization** — сведение дубликатов к одному объекту **внутри owner**.
2. **Event-based pricing** — цена как append-only история.
3. **Snapshot в списках** — фиксация состояния цены на момент добавления в список.
4. **Identity mapping** — разные источники → один объект **в рамках owner**.
5. **Local-first sync** — клиент создаёт локально → синхронизируется с сервером.

---

## 5. Поведение системы (операции)

| Операция | Поведение |
|----------|-----------|
| Создание товара | Новая запись в каталоге или сопоставление с существующим (identity / match) |
| Добавление в список | Выбор товара, опционально offer, фиксация **price_snapshot** |
| Обновление цены | Новый **PriceRecord** (insert) |
| Чтение цены | **latest** по PriceRecord для offer |
| Merge | Доменная операция объединения в canonical **внутри owner** |
| Чтение после merge | API всегда отдаёт **canonical** после resolve |

---

## 6. Консистентность

### Сильные правила

- id immutable;
- delete в домене — запрещён как «жёсткое удаление» (soft / merge);
- цена — immutable (только новые записи).

### Целостность ссылок

Все связи остаются валидными после merge; входящие `good_id` / `store_id` **resolve к canonical**.

---

## 7. Синхронизация (концепция)

- Тип изменений: **append-only** + **идемпотентные** операции.
- Конфликты (MVP): `updated_at`, **last write wins** (можно уточнить позже).
- После merge все клиенты должны прийти к **одному canonical id** для затронутых сущностей.

---

## 8. Производительность (ориентиры)

Частые операции: поиск товаров, latest цена, загрузка списка.

Требования к индексам (на уровне БД):

- по `normalized_name` (таблицы `goods` / `stores`);
- по `(offer_id, recorded_at)` для истории и latest.

Опционально: кеш latest price.

---

## 9. Расширяемость

Система должна выдерживать: импорт, OCR чеков, рекомендации, авто-планирование, аналитику цен, multi-user (через шаринг списков позже).

## 10. Границы ответственности

| Backend | Клиент |
|---------|--------|
| Консистентность, merge, identity resolution, история цен, синк | UX, локальное состояние, optimistic UI |

## 11. Требования к API (уровень ТЗ)

### 11.1 Общие

- **Аутентификация (MVP):** `Authorization: Bearer <token>`, где token однозначно задаёт `owner_id`.
- **Идентификаторы:** клиентские ULID/UUID; сервер **не генерирует** id; операции **идемпотентны**.
- Все операции **scoped** по `owner_id`.
- Предпочтительно **upsert** вместо раздельного create/update где уместно.
- **Merge** — отдельная операция, не «магия» на каждом запросе.

### 11.2 Формат ошибки

```json
{
  "code": "NOT_FOUND",
  "message": "Good not found"
}
```

### 11.3 Основные ресурсы и операции

| Область | Операции (логика) |
|---------|-------------------|
| Goods (товары) | Upsert (`POST /goods`), поиск (`GET /goods?q=`), получение с resolve canonical (`GET /goods/{id}`) |
| Merge | `POST /goods/merge`; кандидаты `GET /goods/{id}/merge-candidates?q=` (exact / prefix / contains / others) |
| Stores | Upsert (`POST /stores`), поиск (`GET /stores?q=`) |
| Offers | Создание с resolve good/store и уникальностью пары (`POST /offers`); офферы по товару (`GET /goods/{id}/offers`) с latest ценой |
| Prices | Только insert (`POST /price-records`); история (`GET /offers/{id}/prices`); опционально latest (`GET /offers/{id}/price/latest`) |
| Lists | Upsert списка (`POST /lists`), список списков (`GET /lists`), детали (`GET /lists/{id}`) |
| List items | Добавление с snapshot (`POST /list-items`), обновление полей (`PATCH /list-items/{id}`): quantity, is_purchased, offer_id |
| Identity | Опционально `POST /good-identities` с уникальностью `(owner, external_id, source)` |

### 11.4 Явно не делать

- delete endpoints как основной способ убирать данные;
- update существующей записи цены;
- глобальные данные без owner;
- автоматический merge без явного решения пользователя/операции.

---

## 12. Итоговая модель (дерево)

```
User (owner)
 ├── Goods (товары)
 ├── Stores
 ├── Offers
 ├── PriceRecords
 ├── Lists
 │    └── ListItems
 └── Identities
```

Итог: **owner-isolated**, **idempotent**, **sync-friendly**, **merge-safe**, с **историей цен** и заделом под **shared lists**.
